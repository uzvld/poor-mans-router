# Roadmap

## Open

### 1. BUG C — the last mile is OMP core, in a shipped binary
**Root cause proven** across 7 cases with provider-payload tracing (`tools/context-tracer/`): the loss is **OMP OpenAI remote compaction**, not a switch bug. On a Responses-API provider OMP keeps `preserveData.openaiRemoteCompaction.replacementHistory` plus a one-line placeholder summary; after a switch to any non-Responses model the placeholder is all the new model sees. Measured in a real 3,300-entry session: 4 remote compactions of 250–300k tokens each → a 933-char placeholder. `docs/investigations/bug-c-context-loss-root-cause.md`.

**Everything reachable from here is done.** The config mitigation is live (`omp config get compaction.methodOrder` → `["snapcompact","handoff","shake","soft"]` — no `remote`), and the router now refuses to be the trigger (Done → "remote-compaction hold").

**Not actionable in this repo:** OMP core should generate a portable summary from `replacementHistory` at switch time instead of substituting the placeholder. That is upstream work in a shipped binary.

### 2. Unclassified model names get no tier — patch drafted, rung decision pending

`classifyModelId()` matches a closed set of **product-name** tokens (generation is never consulted, so `gpt-6-luna` needs nothing from us while `gpt-6-sol` gets nothing at all), `frontier` has no generic paid rung, and `*-sub` classes additionally require `subscriptionLike`. Net: an unrecognised name — and any PAYG seller of a frontier-grade model — can only ever reach `balanced` rung 5 (`best-available`). Live today: `openai-codex/gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.5`, `kilo/openai/gpt-6-astra` (10/50). Counterfactual replay shows `frontier` picking a paid PAYG `strong-chinese` route over a healthy subscription flagship with capacity. Findings, hypothesis table and differential: `docs/investigations/finding-unclassified-model-names.md`.

**Drafted** on branch `finding/unclassified-model-names`: one word-bounded token line in `policy.ts` (`sol`/`terra` → `opus-ish`), 5 red-then-green mutation-proved tests, 126 pass / 0 fail, every non-target route byte-identical before/after on both snapshots. **Not merged and not installed**: it changes which model a session runs on, and the rung (`opus-ish` recommended), the token set, and the PAYG limb all need your call.

**Prototype on the same branch — rungs from the snapshot.** Rung *order* inside every tier is now derived from the last benchmark snapshot (`extension/rungs.ts`, five stated rules, shipped ladder as the fallback) instead of being a hand-written list; `selectForTier` semantics and `policy.yml` are untouched and nothing is installed. 8/8 guards mutation-proved, 138 pass / 0 fail, `bun run test:sim` 5/5, replay tool at `tools/rung-replay/`. On the 2026-09-22 snapshot it lifts `opus-sub` above `astra-sub` (Opus 5 78.0/56.5 vs Astra 76.9/51.0) and `strong-chinese` above `strong-flash-sub`, and with the Anthropic/Codex windows inside reserve the frontier fallback moves off the cheapest flashes while keeping the subscription-first choice (`opencode-go` copies still win). `balanced`/`small`/`free` are byte-identical to their shipped ladders. The same snapshot also showed **Opus 5.5, GPT-6 Sol and GPT-6 Luna have no measurement at all**, and surfaced three intel coverage gaps (`opencode-go` bare ids, dot-vs-dash Claude versions, dated slugs) that made premium subscription routes read as unmeasured. A follow-up commit on the same branch matches intel keys by shape instead of spelling and lifts reach from 95 to 412 of 1203 routes (87 → 347 with a real capability index): 8 more tests, 5 more mutation-proved guards, 146 pass / 0 fail, and the frontier ladder no longer has a pinned rung. The remaining decisions are listed in the finding.

## Done

- **`hermes update` no longer silently un-integrates OMP** (was open) — the 15 core patches in `reapply_omp_patches.py` are wiped by every update, and on 2026-09-19 all 15 were missing: that is why Multica's picker had lost every OMP model (ACP catalog down to the single current-model fallback row; reapplying restored 1245 rows / 1173 `omp:*` / all four `pmr/*`). A hook *inside* hermes-agent cannot fix this — it is deleted before it could run. The re-integration therefore lives in the launcher, outside the replaced tree: `~/.hermes/plugins/model-providers/omp/hermes-launcher.sh`, installed over `~/.local/bin/hermes`. It execs straight through for every command except `update`; after an update it reapplies the patches, rebuilds the Electron app **only** when a renderer patch was re-applied (the update's own build ran against unpatched sources), keeps the update's exit code, and shouts on stderr when an anchor needs hand reconciliation. 10 contract tests (`test_launcher_wrapper.sh`), red-proved by two mutations.
- **Desktop renderer rebuilt and installed** (was open) — `hermes desktop --build-only --force-build` after the reapply; a second run reports "content stamp matches", which is the proof the artifact was built from the patched sources. The stale `/Applications/Hermes.app` (06:51, pre-patch) was swapped via the supported `_install_rebuilt_desktop_app` path: installed and rebuilt `app.asar` now hash identically (`d6067ce0a8fd`).
- **Deploy lock** (was open item 2) — `install.sh`/`uninstall.sh` acquire `$(omp config path)/extensions/.adaptive-router-deploy.lock` by atomic `mkdir`, write `meta.json` (`pid`/`session`/`started_at`), reclaim a lock whose pid is dead or whose age exceeds 600 s, and release via `trap ... EXIT` only when the run created it. Five tests in `scripts/install.test.sh`, each mutation-proved. Found on the way: under macOS bash 3.2 a bare `[[ … ]]` assertion does **not** trip `set -e` unless it is the script's last statement, so the pre-existing assertions in that file were silent no-ops — all standalone assertions are now POSIX `[ … ]`. Live-proved by the install that deployed the remote-compaction hold (lock acquired, released, installed hashes equal to the repo tree).
- **429 / fallback and PAYG-vs-subscription** (was open item 3) — both claims CONFIRMED with mutation-proved tests (`extension/tests/payg-vs-sub.test.ts`) and a report (`docs/investigations/finding-429-payg.md`). A healthy subscription always beats PAYG; a *draining* subscription losing to a healthy PAYG route is the two-pass ladder working as designed (`ranking.ts:182-183`), not a violation. Native fallback carries full history: the router's retry hooks touch only route-health bookkeeping and `shouldRouteBeforeAgentStart` blocks `setModel` for the whole retry, so OMP core owns the continuation end to end.
- **`docs/design.md` DRAINING drift** (was open item 4) — the section claimed a CodexBar pace forecast can independently drive DRAINING. Rewritten to the two mutually-exclusive paths `health.ts` actually implements, with the I2 override stated and every claim traced to a line (`health.ts:54-65`, `102-111`, `128-129`, `148-153`, `163-169`); the misleading `claude-sonnet-5 DRAINING quota pace` example is now an I2 demonstration.
- **Host integration — all four paths answered** (was open item 5) — see `docs/investigations/host-integration-matrix.md`. `omp` directly, `multica → omp`, `paseo → omp` and `multica → hermes → omp` are all governed; the last one's earlier "cannot be governed" verdict was wrong and is corrected there with a live probe (`tools/hermes-path-probe/probe.py`). The final open row is closed too: no Multica launch passes `--no-extensions` — 647 real `omp` launches across every rotated daemon log show only two argv shapes, both without it, and the flag string in the daemon binary belongs to the Claude flag cluster (`docs/investigations/finding-multica-no-extensions.md`).
- **Hermes ⇄ OMP bridge fidelity — all four rows closed** (was open item 6). Plugin-side, in `~/.hermes/plugins/model-providers/omp/`:
  - **Model pinning.** `_pin_model` split the id on the first `/` and swallowed every error, so Multica's prefixed picker ids (`omp:anthropic/claude-fable-5-1`, `omp:openai-codex/gpt-5.6-luna` every 30 min from the hotline cron) produced provider `omp:anthropic` → `Model not found` → the turn silently ran on OMP's persisted current model (`kilo/kilo-auto/efficient`). Now the host prefix is stripped, a refusal raises, an acked-but-unmoved switch raises, and a normalised id warns. `test_model_pin.py`, 4/4 behavioural tests red against the pre-fix file.
  - **Tool calls.** OMP's own tool work now rides Hermes' tool rail instead of being flattened into `[omp:bash]` prose: the profile opts in with `wants_agent_handle`, the core hands `_hermes_agent` to that profile only, and the client reports `tool.started`/`tool.completed` through `agent.tool_progress_callback` — the callback both the ACP adapter (Multica) and the desktop gateway install. `delta.tool_calls` stays `None`, so Hermes still never re-executes finished work. Live: a real `bash` tool produced `tool.started bash args={'command': 'echo …'}` + `tool.completed … is_error=False` with no marker in the transcript. `test_tool_rail.py` (11 tests) and core `tests/agent/test_provider_agent_handle.py` (4 tests, red-proved).
  - **Streaming.** Order, boundaries and interleaving with tool activity verified (`test_stream_fidelity.py`). One real bug found and fixed: `__next__` checked `_failure` only before blocking on the queue, so a consumer parked in `queue.get()` saw the producer's `__done__` first and raised a bare `StopIteration` — an OMP-side failure became a clean, EMPTY answer while the non-streaming path raised. Both paths now agree.
  - **Reasoning.** Correct as written: `thinking_delta` goes to `reasoning`/`reasoning_content` only, never leaks into `content`, on both paths.
  - **Termination.** `finish_reason` is no longer hard-coded `"stop"`: OMP's `message.stopReason` is mapped to the OpenAI vocabulary (`max_tokens`/`truncated` → `length`, `tool_use` → `tool_calls`), and an aborted/cancelled/errored turn raises instead of masquerading as a completed answer.
- **Remote-compaction hold** (BUG C router-side guard) — `extension/compaction-guard.ts`: the router refuses its own switch when the branch's newest compaction is `method: "remote"`, the session is on a Responses-API provider, and the target cannot replay it (different provider, or not a Responses API). It announces `[omp:pmr] switch held: …` once per session and fails open on missing metadata. 8 tests (`extension/tests/compaction-guard.test.ts`) including the hook-level wiring; 5/8 red under an inverted guard.

- **`pmr/*` selectors** — the virtual provider is `pmr`, and the picker offers four tiers: `pmr/frontier`, `pmr/balanced`, `pmr/small` (cheap and fast, paid rungs included) and `pmr/free` (free-only by contract, never spends). Switch markers read `[omp:pmr]`. Upper-case ids were verified to resolve, but lower case matches every other OMP provider id, with `PMR: …` as the display name.
- **First managed turn no longer waits for telemetry** — `before_agent_start` used to await `omp usage` + the CodexBar CLI (28–31 s live). Refreshes are scheduled instead, and the normalized snapshot is persisted in `state.json` (15-minute bound) so a fresh process — every Multica run — routes from last-known data. Live: 7 s including the answer. `first-turn-latency.test.ts`.
- **Dead free routes are learned, not repeated** — a turn OMP does not retry (4xx other than 408/429; Kilo's 404 "model does not exist") never reaches `auto_retry_start`, so `d3b888e` recorded nothing and the `agent_end` handler stamped the dead route as a *success*; a peer session's whole-map `state.json` save then erased whatever anyone recorded. Now `agent_end` classifies the error turn (24 h cooldown for catalog drift, failure otherwise), announces `[omp:pmr] <route> failed; cooled down …`, and `save()` merges per route newest-wins. Live, cold state: 5 dead `kilo/*:free` routes learned one turn each, 6th fresh process answered, every one after that answers first time. 32 of 52 `kilo/*:free` catalog ids are dead on the live gateway. `error-turn-cooldown.test.ts`, `state-concurrent-save.test.ts`, `health.test.ts`. Follow-up in `docs/investigations/multica-repeated-switch-marker.md`.
